# RAG System Architecture Breakdown

In the **SmartCourt** project, the RAG (Retrieval-Augmented Generation) system is divided into two main feature slices (**LawIngestion** and **DocumentReview**) and a set of **Infrastructure Providers**.

## 1. Infrastructure Providers (The Engine)
These are the core integrations that allow you to parse documents, generate embeddings, store vectors, and generate LLM responses.

*   **`IPdfParserProvider` / `PdfPigParserProvider`**
    *   **Description**: Responsible for reading PDF documents and extracting text. It uses the `ArabicTextNormalizer` to handle complex Arabic text extraction and normalization (e.g., removing diacritics, standardizing characters) to ensure high-quality text for chunking and embeddings.
*   **`IEmbeddingProvider` / `GeminiEmbeddingProvider`**
    *   **Description**: This provider is responsible for converting raw text into vector embeddings. It interfaces with the Gemini API to produce high-dimensional representations of text that can be used for semantic similarity comparisons.
*   **`IVectorStoreProvider` / `QdrantVectorStoreProvider`**
    *   **Description**: This is the vector database integration. It is used to store the embeddings generated by the embedding provider alongside metadata (like document IDs, text chunks). It also performs the vector similarity search to retrieve relevant chunks based on a query vector.
*   **`IChatModelProvider` / `DeepSeekChatModelProvider` (and `GeminiChatModelProvider`)**
    *   **Description**: This handles the "Generation" part of RAG. Once relevant legal context is retrieved from Qdrant, this provider is called to send a prompt containing the user's question and the retrieved context to a Chat LLM (like DeepSeek or Gemini) to generate a final answer.

## 2. Feature: LawIngestion (The "Indexing/Preparation" Phase)
This feature slice is responsible for taking raw legal documents (laws, precedents), chunking them, embedding them, and storing them in the vector database so they can be queried later.

*   **Controller**: `LawIngestionController`
    *   **Description**: Exposes HTTP endpoints for admins or system jobs to trigger the ingestion of new laws, regulations, or legal precedents into the system.
*   **Service Interface**: `ILawIngestionService`
*   **Service Implementation**: `LawIngestionService`
    *   **Description**: Contains the core workflow for ingestion. It parses the incoming legal PDF documents using `IPdfParserProvider`, uses the chunker to break them down, calls the `IEmbeddingProvider` to get vector embeddings for each chunk, and finally calls the `IVectorStoreProvider` to store these chunks in Qdrant.
*   **Utility/Domain**: `LegalDocumentChunker`
    *   **Description**: A specialized class that understands how to split long legal texts into smaller, semantically meaningful chunks (e.g., by article or paragraph) while respecting the token limits of the embedding model.
*   **DTOs**:
    *   `IngestLawDocumentRequest`: The payload sent by the client containing the document file to be ingested.
    *   `IngestLawDocumentResponse`: The immediate response confirming the ingestion has started (or completed).
    *   `LawDocumentStatusResponse`: A DTO used to poll or check the status of a long-running ingestion process.
    *   `LawChunkDto`: A representation of a single processed chunk of text before it is sent to the vector store.

## 3. Feature: DocumentReview (The "Retrieval & Generation" Phase)
This feature slice represents the user-facing side of the RAG system. It takes user queries or documents, finds relevant laws from the vector database, and generates legal analysis or answers.

*   **Controllers**: `AskLawController` & `ReviewDocumentController`
    *   **Description**: Exposes endpoints for users (e.g., lawyers) to ask legal questions (`AskLaw`) or submit documents/text for analysis (`ReviewDocument`).
*   **Service Interface**: `IDocumentReviewService`
*   **Service Implementation**: `DocumentReviewService`
    *   **Description**: The heart of the RAG query process. When a user asks a question or submits a document to be reviewed, this service:
        1. (If a document is submitted) Parses it using `IPdfParserProvider`, chunks it, and stores it in a temporary vector collection.
        2. Calls `IEmbeddingProvider` to embed the user's query and retrieve the most relevant facts/chunks from the submitted document.
        3. Combines the user's query and the retrieved document chunks, then embeds this combined context.
        4. Calls `IVectorStoreProvider` to perform a similarity search using that combined vector against the `egyptian_law` collection to retrieve relevant legal articles.
        5. Constructs a comprehensive prompt combining the user's query, the retrieved document context, and the relevant law chunks.
        6. Calls `IChatModelProvider` to generate an informed legal analysis (the "Generation").
*   **DTOs**:
    *   `AskLawRequest`: Contains the user's legal question.
    *   `ReviewDocumentRequest`: Contains a reference to a document uploaded by the user for review.
    *   `AnalyzeResponse`: The final DTO returned to the user containing the LLM-generated answer/analysis, and optionally, the citations/sources (the retrieved chunks) that were used to formulate the answer.
